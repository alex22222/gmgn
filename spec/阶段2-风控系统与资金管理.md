# 阶段2：风控系统与资金管理 — 详细实现规范

> **版本**：v1.0  
> **日期**：2026-07-03  
> **状态**：设计规范（待实施）  
> **适用范围**：GMGN扫链聪明钱包发现 + 自动化跟单系统 — 交易执行阶段  
> **前置依赖**：阶段1（发现+评分+模拟回测）已完成并通过验收

## 1. 设计总则

### 1.1 核心原则

| 优先级 | 原则 | 含义 |
|-------|------|------|
| P0 | 本金安全优先 | 任何情况下不允许单笔亏损超过预设阈值，不允许每日亏损超过硬限制 |
| P0 | 渐进暴露 | 从观察→模拟→小额实盘→全量，每一步必须通过上一阶段的验收数据 |
| P1 | 可验证性 | 所有风控规则必须可量化、可回测、可审计；不接受"感觉良好"的决策 |
| P1 | 最小权限 | 私钥隔离、操作可撤销、自动化权限逐级放开 |
| P2 | 透明可解释 | 每笔交易必须有完整的决策日志、风控校验记录、回测支撑 |

### 1.2 红线约束（不可突破）

1. **不允许未经回测验证的策略直接实盘**：任何新策略必须在模拟环境中运行 ≥ 7 天，胜率 ≥ 55%，夏普比率 ≥ 0.5 方可进入小额实盘。
2. **不允许 Martingale 或 DCA 摊薄亏损**：禁止在亏损头寸上追加投入。
3. **不允许无止损持仓**：每笔交易必须在下单前预设硬止损，触发后必须自动执行，不允许人工干预取消。
4. **不允许超过每日亏损上限**：一旦日亏损达到阈值，当日禁止开新仓，现有持仓按原计划执行。
5. **不允许在未完成安全审计的设备上存储私钥**：私钥仅存储于权限 600 的隔离环境，代码仓库中不得出现任何形式的私钥、助记词或派生路径。

## 2. SMART 子目标

### 子目标 2.1：钱包分级与信号质量验证系统（M1）

**Specific**：建立四级钱包验证体系（观察 → 模拟 → 小额实盘 → 全量跟单），每级配备独立的评分阈值和资金上限。

**Measurable**：
- 观察级：评分 ≥ 80 分，跟踪 ≥ 30 个钱包，记录 7 天完整交易数据
- 模拟级：观察级钱包中胜率 ≥ 60% 且 7 天盈利 > 0 的，自动晋级；每个钱包模拟资金 1000 USDC，全量模拟持仓
- 小额实盘级：模拟级钱包中 14 天胜率 ≥ 65% 且最大回撤 < 30% 的，自动晋级；每个钱包单日上限 100 USDC，单笔上限 50 USDC
- 全量级：小额实盘级钱包中 30 天年化收益 > 50% 且夏普比率 > 1.0 的，人工审核后晋级；每个钱包单日上限 1000 USDC，单笔上限 500 USDC

**Achievable**：基于阶段1已建立的评分体系和 200+ 候选钱包数据，可完成分级筛选。

**Relevant**：钱包分级是风控的第一道闸门，防止低质量信号直接进入实盘。

**Time-bound**：M1 完成时间为 2 周（第 1-2 周）。

**验收标准**：
- [ ] 四级钱包名单以 JSON 文件输出，包含每个钱包的地址、当前级别、评分历史、晋级/降级记录
- [ ] 模拟级钱包已运行 ≥ 7 天模拟跟单，生成模拟盈亏报告
- [ ] 晋级/降级规则由代码自动执行，非人工操作，日志可审计

**失败回退**：
- 若模拟级钱包不足 10 个，暂停全量晋级，返回阶段1扩大候选池
- 若模拟胜率普遍低于 50%，重新校准评分权重，延长观察期至 14 天

### 子目标 2.2：仓位管理与资金分配引擎（M2）

**Specific**：实现三种标准化买入模式（Max Buy、Fixed Buy、Fixed Ratio），并自动适配钱包级别。

**Measurable**：
- Fixed Buy：每单固定金额，观察级 0 SOL（仅观察），模拟级 0.5 SOL，小额实盘级 0.5-1 SOL，全量 1-2 SOL
- Fixed Ratio：按钱包总资金的固定比例（模拟级 2%，小额实盘 5%，全量 10%）
- Max Buy：全量级专用，单次投入不超过该钱包当日剩余配额的 50%
- 每个钱包同时持仓上限：观察级 0（仅跟踪），模拟级 5 个，小额实盘 3 个，全量 5 个

**Achievable**：基于现有 `config/risk_limits.json` 扩展，改动范围限于配置和分配逻辑。

**Relevant**：标准化仓位管理是防止过度暴露和情绪化加仓的核心机制。

**Time-bound**：M2 完成时间为 1 周（第 3 周）。

**验收标准**：
- [ ] 资金分配引擎接收钱包级别 + 目标信号 → 输出精确到 lamport 的买入金额和滑点参数
- [ ] 持仓冲突检测：当钱包已达持仓上限时，新信号自动排队或丢弃，有明确日志
- [ ] 分配结果通过单元测试覆盖 100% 的边界条件（零余额、超额请求、并发信号等）
- [ ] 生成 `data/position_allocations.json` 作为每笔交易的输入

**失败回退**：
- 若 Fixed Ratio 在波动行情下导致仓位过大（单次 > 15% 总资金），自动回退至 Fixed Buy 模式并告警
- 若 Max Buy 触发过于频繁，降低触发阈值或暂停该模式

### 子目标 2.3：止盈止损与订单管理系统（M3）

**Specific**：构建支持市价、限价、止盈止损、追踪止盈、追踪止损的订单管理系统，每笔交易在创建时即绑定完整的退出计划。

**Measurable**：
- 标准止损：-30%（保守）到 -40%（标准），硬止损；触发后全量卖出
- 标准止盈：分级止盈
  - 第一档：+100% 卖出 50% 仓位
  - 第二档：+300% 卖出剩余 50% 仓位的 60%（即总仓位 30%）
  - 第三档：+500% 卖出剩余仓位（即总仓位 20% ride），或设置追踪止盈（回撤 20% 触发）
- 激进变体（可选，需单独回测）：+200% 卖 50%，+500% 卖 30%，+1000% ride 20%
- 所有止盈止损单在买入确认后 3 秒内提交到链上，超时视为失败，触发告警
- 订单状态实时追踪：已提交 → 已确认 → 已生效 → 已触发 → 已成交

**Achievable**：基于 GMGN 官方 CLI 的 `cooking` 命令和条件单能力封装。

**Relevant**：链上交易波动极大，手动盯盘不可行；自动化退出是生存的必要条件。

**Time-bound**：M3 完成时间为 2 周（第 3-4 周）。

**验收标准**：
- [ ] 订单管理系统支持 6 种订单类型（市价、限价、止盈止损、追踪止盈、追踪止损、批量）
- [ ] 每笔交易在创建时生成 `OrderTicket` 对象，包含完整的订单链路、状态机、重试计数
- [ ] 提交延迟 P99 < 5 秒（本地测试网或 devnet 验证）
- [ ] 止损触发成功率 ≥ 99%（模拟测试 1000 次触发）
- [ ] 生成 `data/active_orders.json` 和 `data/order_history.jsonl`，可回溯每笔订单全生命周期

**失败回退**：
- 若链上条件单成功率 < 95%，立即切换为本地监控 + 市价单止损模式（轮询价格，触发后发送市价卖出）
- 若 GMGN API 条件单功能不稳定，降级至第三方 DEX（Raydium/Jupiter）直接路由，绕过 GMGN 中间层
- 若追踪止盈在链上无法可靠实现，改为固定阶梯止盈（已包含在标准模式中）

### 子目标 2.4：滑点与 MEV 防护引擎（M4）

**Specific**：实现三档滑点模式（Auto / Turbo / Anti-MEV）和三档 MEV 防护（Off / Reduced / Secure），根据代币流动性和市场热度自动选择或人工指定。

**Measurable**：
- 滑点配置：
  - Auto：基础 10%，根据 5 分钟波动率动态调整，上限 30%
  - Turbo：固定 20%，用于快速进出（抢开盘）
  - Anti-MEV：固定 50% 或更高，用于高热度代币，配合 Secure MEV 防护
- MEV 防护配置：
  - Off：无防护，最低额外费用，仅用于冷启动测试
  - Reduced：优先费 0.01-0.03 SOL，基础防护
  - Secure：优先费 0.05-0.1 SOL，配合 Jito MEV 保护或同类服务
- 动态选择规则：
  - 市值 < 50K 或 5 分钟交易量 < 10K：Auto + Off
  - 市值 50K-500K 或交易活跃：Auto + Reduced
  - 市值 > 500K 或热搜榜：Turbo/Anti-MEV + Secure
- 每笔交易的实际滑点和优先费记录到 `data/slippage_audit.jsonl`

**Achievable**：基于 GMGN CLI 的滑点和 MEV 参数封装，结合市场数据动态计算。

**Relevant**：meme 代币滑点可能高达 30-50%，MEV 攻击（三明治攻击）在 Solana 上频繁发生；不当的滑点设置会导致无法成交或被套利机器人掠夺。

**Time-bound**：M4 完成时间为 1 周（第 4 周）。

**验收标准**：
- [ ] 滑点/MEV 选择引擎可根据输入信号自动推荐参数组合，人工可覆盖
- [ ] 实际成交滑点与预设滑点偏差 > 20% 时触发告警（"滑点失控"）
- [ ] Secure 模式下 MEV 被攻击率 < 1%（通过对比交易前后价格验证）
- [ ] 优先费动态调整：网络拥堵时（参考 Solana 优先费中位数）自动提升 0.01 → 0.03 → 0.05 SOL

**失败回退**：
- 若 Anti-MEV 模式导致连续 3 笔交易失败（超时或拒绝），自动降级为 Turbo + Reduced
- 若优先费 > 0.1 SOL 仍无法成交，暂停该代币交易，标记为"高摩擦"
- 若 MEV 攻击率 > 5%，紧急切换至专用 MEV 保护 RPC（Jito 或 Helius）

### 子目标 2.5：每日亏损限制与熔断机制（M5）

**Specific**：实现硬性的日亏损限制和三级熔断机制（黄灯/橙灯/红灯），防止情绪化交易和连续亏损导致的本金大幅回撤。

**Measurable**：
- 日亏损限制：
  - 模拟级：日亏损 ≥ 5% 时暂停开新仓
  - 小额实盘：日亏损 ≥ 3% 时暂停开新仓
  - 全量：日亏损 ≥ 2% 时暂停开新仓
- 熔断机制：
  - 黄灯（预警）：日亏损达到限制阈值的 50%，发送告警，降低新仓位 50%
  - 橙灯（限制）：日亏损达到限制阈值，禁止开新仓，现有持仓正常执行退出计划
  - 红灯（紧急）：日亏损达到限制阈值的 200%，立即取消所有未成交订单，对所有持仓发送市价清仓单
- 周亏损限制：周亏损 ≥ 10%（全量）/ 15%（小额）/ 20%（模拟）时，当周剩余时间禁止开新仓
- 月度回撤限制：从月初最高净值计算，最大回撤 ≥ 20% 时，当月进入"只平仓不建仓"模式

**Achievable**：基于现有 `daily_loss_limit_percent` 扩展，增加状态机和熔断逻辑。

**Relevant**：meme 代币市场波动极大，连续亏损很常见；硬性限制是保护本底的最后防线。

**Time-bound**：M5 完成时间为 1 周（第 5 周）。

**验收标准**：
- [ ] 日/周/月亏损状态自动计算，每 5 分钟刷新一次，存储到 `data/risk_status.json`
- [ ] 熔断触发后，所有新信号在 3 秒内收到 "blocked_by_risk_limit" 拒绝响应
- [ ] 红灯触发后，市价清仓单在 10 秒内提交完成（测试网验证）
- [ ] 熔断状态变更记录到 `data/circuit_breaker_log.jsonl`，包含触发原因、净值快照、恢复条件
- [ ] 提供人工恢复接口：红灯状态需人工确认 + 风险评估报告后方可解除

**失败回退**：
- 若净值计算数据源故障（无法获取持仓价格），立即触发橙灯（限制新仓），使用最后已知价格保守估算
- 若红灯触发后市价清仓失败（网络拥堵或流动性枯竭），启用 "逃生模式"：以最大容忍滑点（50%）分批卖出，每批间隔 30 秒
- 若连续 3 日触发红灯，系统自动降级至模拟级，暂停所有实盘，直至人工审核

### 子目标 2.6：交易模拟与回测验证系统（M6）

**Specific**：构建完整的模拟交易引擎，能够基于真实链上数据回放，验证所有风控策略的有效性。

**Measurable**：
- 模拟引擎：
  - 输入：历史钱包交易记录（从阶段1获取的聪明钱包地址）
  - 处理：按当前风控规则（仓位、止盈止损、滑点、手续费 1%）逐笔模拟交易
  - 输出：模拟盈亏报告、最大回撤、夏普比率、胜率、盈亏比
- 回测覆盖：
  - 最少 30 天历史数据
  - 至少 50 个不同钱包的回测
  - 至少 500 笔模拟交易
- 关键指标：
  - 整体胜率 ≥ 55%（目标 60%+）
  - 夏普比率 ≥ 0.5（目标 1.0+）
  - 最大回撤 < 30%（目标 < 20%）
  - 盈利因子（总盈利/总亏损）≥ 1.5（目标 2.0+）

**Achievable**：利用历史候选数据和已发现的聪明钱包交易历史进行回放。

**Relevant**：没有回测验证的风控策略是盲目飞行；模拟是实盘前的必经阶段。

**Time-bound**：M6 完成时间为 2 周（第 5-6 周）。

**验收标准**：
- [ ] 回测报告 `data/backtest_report.md` 包含完整的统计指标、分钱包表现、分时段表现、 worst-case 场景分析
- [ ] 回测可重复：相同输入在相同版本代码下产生相同输出（确定性验证）
- [ ] 回测参数可配置：止盈止损档位、滑点、手续费、仓位模式均可在 `config/backtest.json` 中调整
- [ ] 回测通过后，automation gate 的 `positive_expectancy_after_costs` 和 `paper_or_shadow_results_available` 字段可设为 true

**失败回退**：
- 若回测胜率 < 50%，返回调整评分权重和风控参数，重新运行回测
- 若回测最大回撤 > 40%，收紧止损阈值（-30% → -25%）和仓位限制（10% → 5%），重新回测
- 若历史数据不足（< 30 天或 < 50 个钱包），延长数据收集期，暂不进入下一阶段

### 子目标 2.7：执行层集成与 Kill Switch（M7）

**Specific**：集成 GMGN CLI / API 作为执行后端，实现安全的自动化下单，同时提供物理级 Kill Switch 能力。

**Measurable**：
- GMGN 集成：
  - 使用 `gmgn-cli`（npm）或 `gmgnapi`（Python WebSocket）作为执行通道
  - 优先使用 `cooking` 命令：一键买入并自动附加止盈止损条件单
  - 支持 6 种订单类型：市价、限价、止盈止损、追踪止盈、追踪止损、多钱包批量
  - 支持三种滑点模式和三种 MEV 防护配置透传
- 执行监控：
  - 每笔交易从信号生成到链上确认的全链路延迟 < 10 秒（P99）
  - 交易失败自动重试：最多 3 次，每次间隔 5 秒，失败原因分类记录
  - 交易成功但滑点超预期时触发 "slippage_warning" 告警
- Kill Switch：
  - 软 Kill：取消所有活跃订单，禁止新订单，现有持仓保留（可通过 UI/CLI 触发）
  - 硬 Kill：软 Kill + 市价清仓所有持仓（需二次确认，可通过 UI/CLI/远程消息触发）
  - 紧急 Kill：检测到异常（如私钥泄露、API 被篡改、净值暴跌）时自动触发硬 Kill，无需人工确认
  - Kill Switch 状态持久化到 `data/kill_switch.state.json`，重启后保持

**Achievable**：基于已有的 execution venue config 和 GMGN 工具链封装。

**Relevant**：执行层是资金与市场的接口，必须安全、可靠、可立即终止。

**Time-bound**：M7 完成时间为 2 周（第 6-7 周）。

**验收标准**：
- [ ] GMGN CLI 命令封装层通过测试，所有参数正确透传，无注入风险
- [ ] 私钥仅通过环境变量或 `~/.config/gmgn/.env`（权限 600）读取，代码中不硬编码
- [ ] Kill Switch 可通过本地 CLI (`python -m gmgn_monitor.kill_switch --action hard`) 和远程消息（如 Telegram 机器人指令 `/killswitch hard`）触发
- [ ] Kill Switch 触发后，所有持仓在 60 秒内完成市价清仓（测试网验证）
- [ ] 执行层有独立的健康检查：`python -m gmgn_monitor.execution_health`，每 5 分钟运行一次
- [ ] 生成 `data/execution_audit.jsonl`，记录每笔交易的全链路日志（信号 → 风控校验 → 下单 → 确认 → 退出）

**失败回退**：
- 若 GMGN API 不稳定（成功率 < 90%），切换至备用执行通道（Jupiter SDK 直接路由）
- 若 GMGN CLI 出现安全漏洞或异常行为，立即暂停使用，隔离相关私钥，切换至备用通道
- 若 Kill Switch 无法通过远程触发，启用本地定时检查（cron 每 1 分钟检查远程状态文件或消息队列）
- 若市价清仓导致极端滑点损失（> 30%），启用分批清仓（每批 25%，间隔 30 秒）

### 子目标 2.8：全链路监控与审计日志（M8）

**Specific**：构建覆盖信号、风控、执行、结算全链路的监控和审计系统，确保每一笔交易都可追溯、可审计、可复盘。

**Measurable**：
- 审计维度：
  - 信号审计：谁（哪个钱包）/ 何时 / 什么代币 / 为什么（评分明细）
  - 风控审计：仓位计算 / 止盈止损参数 / 滑点/MEV 选择 / 熔断状态
  - 执行审计：订单类型 / 提交时间 / 确认时间 / 交易哈希 / 实际滑点 / 优先费
  - 结算审计：买入价 / 卖出价 / 盈亏金额 / 盈亏百分比 / 手续费 / 耗时
- 日志标准：
  - 所有日志输出为结构化 JSON（JSONL），存储到 `data/audit/` 目录
  - 按日期分片：`audit/YYYY-MM-DD/`
  - 保留期限：原始日志 ≥ 90 天，聚合报告 ≥ 365 天
- 监控告警：
  - 交易失败率 > 5% → 告警
  - 止损触发率 > 40% → 告警（可能信号质量下降）
  - 平均滑点 > 预设值 20% → 告警
  - 日亏损 > 阈值 50% → 黄灯预警
  - 任何异常错误（API 异常、私钥访问异常、权限变更）→ 立即告警
- 仪表盘：
  - 实时显示：总资产、日盈亏、持仓列表、活跃订单、钱包分级分布、信号质量趋势
  - 刷新频率：资产数据 30 秒，持仓数据 10 秒，信号数据 实时

**Achievable**：基于现有 dashboard 和 report 模块扩展，增加交易执行维度。

**Relevant**：没有审计的系统不可信；没有监控的风控是盲风控。

## 4. 算法/逻辑设计

### 4.1 钱包分级评分算法

#### 4.1.1 综合评分公式

```
Score = α·WinRateScore + β·ProfitScore + γ·ConsistencyScore + δ·RiskScore + ε·SizeScore

其中：
  α = 0.25, β = 0.25, γ = 0.20, δ = 0.20, ε = 0.10

WinRateScore = min(WinRate_30d / 0.70, 1.0) × 100
ProfitScore = min(Profit_30d_USD / 50000, 1.0) × 100
ConsistencyScore = max(0, 1 - (WeeklyTxCount - 50) / 450) × 100  # 50-100笔最优，>500惩罚
RiskScore = max(0, 1 - MaxDrawdown_30d / 0.30) × 100
SizeScore = min(AvgPositionSize_USD / 10000, 1.0) × 100
```

**硬性过滤条件**（任一不满足直接排除）：
- 胜率 < 55% → 排除
- 周交易笔数 > 500 或 < 10 → 排除（机器人或僵尸）
- 平均持仓周期 < 4 小时 → 排除（高频刷单）
- 稳定币持仓 < 500 USD → 排除（资金实力不足）
- 近30天利润 < 0 → 排除（亏损钱包）

### 4.2 资金分配算法

#### 4.2.1 三种买入模式

```python
def calculate_buy_amount(signal: SignalEvent, wallet: SmartWallet, portfolio: Portfolio) -> dict:
    level = wallet.level
    
    if signal.buy_mode == 'fixed_buy':
        amount = LEVEL_FIXED_BUY_MAP[level]  # observation: 0, simulation: 0.5, tiny_live: 0.5-1, full: 1-2
    
    elif signal.buy_mode == 'fixed_ratio':
        ratio = LEVEL_RATIO_MAP[level]  # simulation: 0.02, tiny_live: 0.05, full: 0.10
        amount = portfolio.total_equity_usd * ratio
    
    elif signal.buy_mode == 'max_buy':
        daily_remaining = portfolio.daily_remaining_budget
        amount = min(daily_remaining * 0.50, LEVEL_MAX_BUY_MAP[level])
    
    # 约束检查
    amount = min(amount, LEVEL_SINGLE_MAX_MAP[level])  # 单笔上限
    amount = min(amount, portfolio.daily_remaining_budget)  # 日预算上限
    
    # 持仓冲突检查
    open_positions = portfolio.get_open_positions(wallet.address)
    if len(open_positions) >= LEVEL_POSITION_LIMIT_MAP[level]:
        return {'status': 'blocked', 'reason': 'position_limit_reached'}
    
    # 集中度检查：同一钱包在单一代币上不超过总资金的 LEVEL_CONCENTRATION_LIMIT_MAP[level]
    existing_position = portfolio.get_position(wallet.address, signal.token_address)
    if existing_position:
        new_total = existing_position.value_usd + amount
        if new_total > portfolio.total_equity_usd * LEVEL_CONCENTRATION_LIMIT_MAP[level]:
            amount = portfolio.total_equity_usd * LEVEL_CONCENTRATION_LIMIT_MAP[level] - existing_position.value_usd
            if amount <= 0:
                return {'status': 'blocked', 'reason': 'concentration_limit_reached'}
    
    return {'status': 'approved', 'amount_usd': round(amount, 2), 'amount_sol': usd_to_sol(amount)}
```

#### 4.3.3 追踪止盈实现

```python
def update_trailing_stop(position: PositionRecord, current_price: float) -> OrderExecution | None:
    # 更新最高 seen 价格
    if current_price > position.max_price_seen:
        position.max_price_seen = current_price
    
    # 计算追踪止损触发价
    if position.trailing_stop_distance_percent:
        trigger_price = position.max_price_seen * (1 - position.trailing_stop_distance_percent / 100)
    else:
        return None
    
    # 检查是否触发
    if current_price <= trigger_price and position.status == 'open':
        # 提交市价卖出单
        return create_market_sell_order(
            position=position,
            quantity=position.remaining_quantity,  # 卖出剩余全部
            reason=f'trailing_stop_triggered_at_{trigger_price:.6f}'
        )
    
    return None
```

### 4.4 滑点与 MEV 动态选择算法

```python
def select_slippage_and_mev(signal: SignalEvent) -> dict:
    mc = signal.market_cap
    vol_5m = signal.volume_5m
    
    # 热度指标
    heat_score = (vol_5m / max(mc, 1)) * 1000  # 无量纲热度分
    
    if mc < 50000 or heat_score < 1.0:
        return {
            'slippage_mode': 'auto',
            'slippage_percent': 10.0,
            'mev_protection': 'off',
            'priority_fee_sol': 0.005
        }
    elif mc < 500000 or heat_score < 5.0:
        return {
            'slippage_mode': 'auto',
            'slippage_percent': 20.0,
            'mev_protection': 'reduced',
            'priority_fee_sol': 0.015
        }
    else:
        # 高热度，强防护
        base_slippage = min(30.0 + heat_score * 2, 50.0)
        return {
            'slippage_mode': 'anti_mev',
            'slippage_percent': base_slippage,
            'mev_protection': 'secure',
            'priority_fee_sol': 0.05
        }

# 优先费动态调整（基于 Solana 网络状态）
def adjust_priority_fee(base_fee: float, network_median_fee: float) -> float:
    if network_median_fee > 0.02:  # 网络拥堵
        return min(base_fee * 2, 0.1)  # 翻倍，但上限 0.1 SOL
    return base_fee
```

### 4.5 熔断状态机

```
状态：
  green   → 正常运行，允许所有操作
  yellow  → 预警状态，仓位降低 50%，发送告警
  orange  → 限制状态，禁止开新仓，现有持仓正常退出
  red     → 紧急状态，取消所有订单，市价清仓所有持仓

触发条件：
  green → yellow:  日亏损 ≥ 日限额的 50%
  yellow → orange: 日亏损 ≥ 日限额
  orange → red:    日亏损 ≥ 日限额的 200% 或检测到异常事件
  red → green:     人工确认 + 风险评估报告通过

自动恢复：
  yellow → green:  日亏损 < 日限额的 30% 且持续 2 小时
  orange → yellow: 次日零点自动降级（仅每日首次）
  red → orange:    不允许自动恢复，必须人工干预
```

### 4.6 回测引擎逻辑

```python
def run_backtest(wallet_addresses: list[str], 
                 start_date: str, 
                 end_date: str, 
                 risk_config: dict) -> BacktestReport:
    
    results = []
    for wallet in wallet_addresses:
        trades = fetch_historical_trades(wallet, start_date, end_date)
        
        for trade in trades:
            # 模拟风控过滤
            if not passes_signal_filter(trade, risk_config):
                continue
            
            # 模拟仓位分配
            allocation = simulate_allocation(trade, risk_config)
            if allocation['status'] != 'approved':
                continue
            
            # 模拟入场
            entry_price = trade.price * (1 + slippage/100) * (1 + fee/100)
            
            # 模拟持仓直到退出
            holding_period = fetch_holding_period(trade)
            price_history = fetch_price_history(trade.token, trade.entry_time, 
                                                trade.entry_time + holding_period)
            
            exit_price = simulate_exit(price_history, entry_price, risk_config)
            
            # 计算盈亏
            pnl = (exit_price - entry_price) / entry_price * 100
            results.append({
                'wallet': wallet,
                'entry': entry_price,
                'exit': exit_price,
                'pnl_percent': pnl,
                'holding_hours': holding_period.total_seconds() / 3600
            })
    
    return compute_backtest_metrics(results)
```

## 5. Loop Engineering 反馈循环

### 5.1 五级反馈闭环

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           Loop Engineering 架构                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  Loop 1: 信号质量循环 (Signal Quality Loop)                                 │
│  ─────────────────────────────────────────────                               │
│  收集 → 评分 → 模拟跟单 → 对比真实结果 → 校准评分权重 → 重新评分              │
│  周期：每日                                                                  │
│  验证：模拟盈亏与真实盈亏的相关系数 > 0.7                                    │
│                                                                             │
│  Loop 2: 钱包分级循环 (Wallet Level Loop)                                     │
│  ─────────────────────────────────────────────                               │
│  观察 → 晋级 → 实盘 → 跟踪表现 → 降级/维持/晋级 → 调整分级阈值                │
│  周期：每日（自动评估），每周（人工审核）                                    │
│  验证：晋级后 7 天表现不劣于晋级前表现                                       │
│                                                                             │
│  Loop 3: 风控参数循环 (Risk Parameter Loop)                                 │
│  ─────────────────────────────────────────────                               │
│  设定参数 → 回测 → 模拟实盘 → 收集真实结果 → 分析回撤/胜率/盈亏比             │
│          → 调整参数 → 重新回测                                              │
│  周期：每周                                                                  │
│  验证：新参数在回测中夏普比率 ≥ 旧参数                                      │
│                                                                             │
│  Loop 4: 执行质量循环 (Execution Quality Loop)                              │
│  ─────────────────────────────────────────────                               │
│  下单 → 监控确认 → 记录实际滑点/费用 → 对比预设 → 调整滑点/MEV策略            │
│       → 优化下单时机和参数                                                   │
│  周期：每笔交易                                                              │
│  验证：实际滑点 < 预设滑点 * 1.2 的比率 > 90%                               │
│                                                                             │
│  Loop 5: 系统健康循环 (System Health Loop)                                  │
│  ─────────────────────────────────────────────                               │
│  运行监控 → 检测异常 → 触发 Kill Switch/告警 → 人工/自动修复 → 验证修复       │
│  周期：每 5 分钟（自动），实时（异常触发）                                   │
│  验证：doctor 命令返回 OK，所有检查项通过                                     │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 具体反馈机制

#### 5.2.1 信号质量校准（Loop 1）

**收集指标**：
- 信号发出后 5m / 30m / 1h / 4h / 24h 的价格变化
- 信号与真实钱包交易的吻合度（时间差 < 2 分钟，价格差 < 5%）

**校准规则**：
- 若高评分信号（> 85 分）24h 后亏损率 > 50%，降低该评分维度权重 10%
- 若低评分信号（60-70 分）24h 后盈利率 > 50%，提升该评分维度权重 5%
- 每月重构一次评分模型，使用过去 30 天数据

#### 5.2.2 钱包分级校准（Loop 2）

**收集指标**：
- 晋级后 7 天/14 天/30 天表现 vs 晋级前同期
- 降级后是否恢复

**校准规则**：
- 若 simulation → tiny_live 晋级后 14 天亏损率 > 40%，提高 tiny_live 晋级门槛（胜率 65% → 70%）
- 若 tiny_live → full 晋级后 30 天夏普 < 0.5，降低 full 仓位上限或增加人工审核环节
- 每季度review分级阈值，基于历史数据优化

#### 5.2.3 风控参数校准（Loop 3）

**收集指标**：
- 止损触发率、止盈触发率、平均盈亏比
- 最大回撤、夏普比率、胜率
- 实际 vs 模拟的差异（滑点、费用、延迟）

**校准规则**：
- 止损触发率 > 40%：收紧入场条件或降低止损阈值（-35% → -30%）
- 平均盈亏比 < 1.5：优化止盈阶梯（增加第一档卖出比例）
- 实际表现持续劣于模拟 > 20%：增加滑点保守系数、提高优先费

#### 5.2.4 执行质量校准（Loop 4）

**收集指标**：
- 下单到确认延迟（P50/P95/P99）
- 实际滑点 vs 预设滑点
- 交易失败原因分布（网络/流动性/合约/其他）
- 优先费 vs 确认速度的关系

**校准规则**：
- P99 延迟 > 10 秒：增加优先费 0.01 SOL 或切换 RPC 节点
- 实际滑点 > 预设 1.5 倍 > 5%：提升该代币类型/市值区间的默认滑点
- 失败率 > 5%：检查 GMGN API 稳定性，必要时切换备用通道

#### 5.2.5 系统健康校准（Loop 5）

**收集指标**：
- 系统资源使用（CPU/内存/磁盘）
- 数据流延迟（信号采集 → 风控校验 → 下单）
- 审计日志完整性
- 安全事件（未授权访问、异常进程）

**校准规则**：
- 磁盘使用 > 80%：归档旧日志，告警
- 任何安全检查失败：触发 doctor 深度诊断，必要时橙灯/红灯
- 安全事件：立即硬 Kill，人工介入调查

### 7.2 系统性失败的回退

#### 场景 A：连续多日亏损

1. 第 1 日触发黄灯：自动降低仓位 50%
2. 第 2 日触发橙灯：禁止新仓，仅执行现有退出计划
3. 第 3 日触发红灯：全部清仓，系统降级至模拟级
4. 人工复盘：分析信号质量、市场环境、参数设置
5. 调整策略后，重新运行回测，通过后方可逐步恢复

#### 场景 B：GMGN 服务不可用

1. 检测：连续 3 次 API 调用失败或超时 > 30 秒
2. 切换：自动切换至备用执行通道（Jupiter SDK / Raydium SDK）
3. 限制：切换期间仅允许小额交易（Fixed Buy 0.5 SOL），滑点提高 20%
4. 恢复：GMGN 连续 10 分钟可用且成功率 > 95% 后，逐步恢复

#### 场景 C：私钥或安全异常

1. 检测：任何未授权私钥访问、异常进程、文件权限变更
2. 立即：硬 Kill，取消所有订单，尝试市价清仓
3. 隔离：将相关钱包资金转移到冷钱包（预设备用地址）
4. 调查：审查日志，检查系统完整性，确认安全后方可恢复

#### 场景 D：市场极端波动（黑天鹅）

1. 检测：Solana 网络 TPS 骤降、大量代币同时暴跌、Gas 费暴涨
2. 响应：立即橙灯，禁止新仓；若持续 10 分钟则红灯
3. 清仓：分批市价卖出（每批 20%，间隔 1 分钟），避免冲击
4. 恢复：市场稳定后（网络 TPS 恢复，Gas 正常），人工审核恢复

| 私钥访问 | 环境变量注入 | 代码中不硬编码，不打印 |
| 签名隔离 | 独立进程 / 硬件钱包 | 高价值钱包使用 Ledger/Trezor |
| 执行隔离 | 容器化（Docker） | 交易执行层与监控层分离容器 |
| 网络隔离 | 防火墙白名单 | 仅允许访问 Solana RPC 和 GMGN 服务 |
| 审计 | 不可变日志 | 审计日志写入只追加存储，禁止修改 |

## 10. 附录

### 10.1 关键计算公式速查

| 指标 | 公式 |
|------|------|
| 胜率 | 盈利交易数 / 总交易数 |
| 盈亏比 | 平均盈利额 / 平均亏损额 |
| 夏普比率 | (年化收益率 - 无风险利率) / 年化收益率标准差 |
| 最大回撤 | max((峰值 - 谷值) / 峰值) |
| 盈利因子 | 总盈利 / 总亏损（绝对值） |
| 日盈亏% | (当日净值 - 当日开始净值) / 当日开始净值 × 100 |
| 仓位集中度 | 单一代币价值 / 总资产净值 |
| 滑点% | (实际成交价 - 预期价) / 预期价 × 100 |
